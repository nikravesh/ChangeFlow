**بخش اول — سؤالات مفهومی (۵ سؤال)**

**راهنما:** پاسخ‌ها را تحلیلی و با زبان خودتان بنویسید. تعریف اصطلاحات یا کپی از مستندات کافی نیست. در صورت نیاز از مثال فنی در Stack خودتان استفاده کنید.

**سؤال ۱ — Constitution و حاکمیت معماری**

تیم شما تصمیم گرفته تمام Business Logic در لایهٔ Domain یا Application قرار بگیرد و API فقط مسئول دریافت درخواست و ارائهٔ پاسخ باشد.

Coding Agent یک قابلیت را پیاده‌سازی کرده و همهٔ Testها موفق شده‌اند؛ اما بخشی از Business Logic مستقیماً داخل Controller یا Endpoint نوشته شده است.

- چه تفاوتی بین موفقیت Testها و رعایت اصول معماری وجود دارد؟ از نظر عملکردی سیستم درست کار می کند و تست ها موفق هستند ولی اصول معماری و تصمیم گرفته شده نقض شده است و تضمینی بر رعایت شدن اصول معماری نیست. طبق اصول معماری نباید بیزینس در لایه controller باشد و این نشانه نشت بیزینس می باشد. و وابستگی بالا می رود و قابلیت استفاده مجدد کاهش پیدا می کند و نگهداری و تست مستقل دشوار و پیچیده می شود
- قاعدهٔ جداسازی مسئولیت‌ها باید در Constitution، Plan یا Tasks ثبت شود؟ چرا؟  در Constitution. به دلیل اینکه مسئولیت ها یک اصل معماری در کل پروژه می باشند و باید در تمام لایه ها و قابلیت ها (feature) رعایت شوند.
- چگونه می‌توان در توسعه‌های بعدی از تکرار این مشکل جلوگیری کرد؟ باید بصورت صریح در قوانین سراسری پروژه که در مرحله Constitution تعریف می شود ذکر شود تا Agent چیزی را فرض نکند و حدس نزند. و هنگام اجرای مرحله Plan و ،Tasks طبق قوانین تعریف شده پیش برود.

**سؤال ۲ — Specify و Clarify**

مالک محصول می‌گوید:

«کارمندان بتوانند درخواست ثبت کنند و مدیرها بعد از بررسی، درخواست‌ها را تأیید کنند.»

Coding Agent فرض می‌کند هر مدیری می‌تواند درخواست خودش را نیز تأیید کند.

- آیا Agent مجاز است این تصمیم را بدون تأیید مالک محصول نهایی کند؟ خیر. در روش SDD نباید چیزی فرض شود یا حدس زده شود باید همه قوانین صریح و واضح بیان شود. این مورد باید با مالک محصول درمیان گذاشته شود و نتیجه در specification ثبت شود که در طراحی و پیاده سازی و تست لحاظ شود.
- تفاوت Assumption با تصمیم تأییدشدهٔ مالک محصول چیست؟ تصمیمات تایید شده قابلیت برنامه ریزی و پیاده سازی دارند ولی فرضیات باید به تایید مالک محصول برسد و به مرحله تایید شده برسند و تازمانی که به مرحله تایید شده نرسیده باشند نباید پیاده سازی انجام شود. و همچنین فرضیات قابلیت اتکا و اعتبار ندارند
- حداقل دو ابهام مهم دیگر در این درخواست پیدا کنید. \
      - آیا هر مدیری می‌تواند درخواست تمام کارمندان را تأیید کند یا فقط مجاز به تأیید درخواست کارمندان زیرمجموعه خودش است؟\
      - آیا مدیر می‌تواند درخواست را رد کند؟ در صورت رد شدن، آیا ثبت دلیل رد الزامی است؟\
      - درخواست چه وضعیت‌هایی می‌تواند داشته باشد؟ مثلاً Pending، Approved و Rejected
- کدام ابهام‌ها باید در Specify برجسته شوند و Clarify چه نقشی در رفع آن‌ها دارد؟ در مرحله Specify باید ابهام‌هایی برجسته شوند که بر رفتار سیستم، قوانین کسب‌وکار و معیارهای پذیرش تأثیر می‌گذارند. مرحله Clarify پرسش هایی مطرح می شود و با دریافت پاسخ ابهام ها یا تناقض هایی که وجود دارد را برطرف می کند

**سؤال ۳ — Requirement در برابر Design Decision**

در Specification آمده است:

«هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا شود.»

توسعه‌دهنده پیشنهاد می‌کند یک فیلد عددی به نام ContentRevision اضافه کنیم.

- کدام بخش Requirement است و کدام بخش Design Decision؟ بخش "هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا شود" مربوط به نیازمندی می باشد و قسمت توسعه دهنده تصمیم طراحی می باشد.
- چرا بهتر است مکانیزم فنی در Plan/Research بررسی شود؟ Plan/Research متمرکز بر بررسی و انتخاب راهکار فنی هستند و این مرحله باعث می شود بتوان راهکار های مختلف را از نظر مزایا/معایب مقایسه کرد.
- حداقل دو راهکار جایگزین برای تشخیص محتوای تأییدشده پیشنهاد کنید و Trade-off آن‌ها را توضیح دهید.\
  ` `- ContentHash : هنگام تأیید درخواست، هش محتوای تأییدشده با الگوریتمی مانند SHA-256 محاسبه و ذخیره می‌شود. مزایا : امکان بررسی یکسان بودن محتوای فعلی با محتوای تأییدشده. معایب : هزینه پردازشی بیشتر\
      - باطل کردن تایید در صورت تغییر محتوا : هر زمان محتوای یک درخواست تأییدشده تغییر کند، وضعیت تأیید آن به‌صورت خودکار باطل می‌شود

**سؤال ۴ — Tasks و Analyze**

برای یک Feature، تعداد ۳۰ Task تولید شده و هر Requirement حداقل به یک Task مرتبط است. با این حال، یک Task به دیتابیس آماده نیاز دارد، در حالی که Migration دیتابیس در Task بعدی تعریف شده است. همچنین دو Task دارای نشانگر [P] باید فایل مشترکی را تغییر دهند.

- چه مشکلاتی در Dependency و Parallelism وجود دارد؟ در Dependency ترتیب Taskها صحیح نیست؛ زیرا Task وابسته قبل از Task مربوط به Migration قرار گرفته و پیش‌نیاز اجرای آن فراهم نشده است. در Parallelism نیز دو Task دارای نشانگر [P] قرار است فایل مشترکی را تغییر دهند که ممکن است باعث Conflict و تداخل در تغییرات شود.
- انتظار دارید Analyze چه Findingهایی گزارش کند؟ انتظار می‌رود Analyze مشکلات مربوط به ترتیب و وابستگی Taskها و تداخل در اجرای موازی وظایف را شناسایی و برای اصلاح گزارش کند.
- آیا پوشش ۱۰۰٪ Requirementها توسط Tasks، آمادگی قطعی برای Implement را ثابت می‌کند؟ چرا؟ خیرقبل از پیاده سازی باید علاوه بر پوشش نیازمندی ها ترتیب اجرا و تداخل احتمالی بررسی شود و در صورت نیاز اصلاح گردد.

**سؤال ۵ — Implement، Validation و Converge**

Coding Agent گزارش داده است:

«تمام Taskها تکمیل شده‌اند؛ پروژه Build شده و ۱۲۰ Test همگی Passed هستند.»

اما در Code Review متوجه می‌شوید یک قاعدهٔ امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز ارزیابی نشده است.

- آیا Feature قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است؟ خیر
- تفاوت Build، Test، Validation و Acceptance چیست؟ موفقیت Build نشان می‌دهد کد کامپایل شده و خطاهای مانع Build وجود ندارند؛ اما تضمین‌کننده صحت عملکرد نیست. ست‌ها بررسی می‌کنند که رفتار سیستم در سناریوهای مشخص با نتایج مورد انتظار مطابقت دارد. Validation بررسی می‌کند که Feature پیاده‌سازی‌شده با نیازمندی‌های کسب‌وکار، Specification و هدف مورد انتظار مطابقت داشته باشد و Acceptance مرحله تأیید نهایی Feature توسط مرجع مسئول می باشد.
- Converge در این وضعیت چه نقشی دارد و چه تفاوتی با Analyze دارد؟ Analyze برای بررسی سازگاری و کیفیت Artifactهای تولیدشده استفاده می‌شود برای مثال شناسایی تناقض بین spec.md، plan.md و tasks.md و اینکه analyze قبل از پیاده سازی انجام می شود و فایلی تغییر نمی کند در صورتی که Converge بعد از پیاده سازی انجام می شود و اگر نقصی وجود داشته باشد task ایجاد کرده و در task.md اضافه می کند.
- اگر Converge شکاف جدیدی پیدا کند، مسیر اصلاح چیست؟  اگر در این مرحله شکافی پیدا شود Task جدید باید در task.md تعریف شود و مجددا پیاده سازی انجام شود و  دوباره مرحله Coverage اجرا شود تا از رفع شکاف اطمینان حاصل شود.
