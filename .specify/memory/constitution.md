# قانون اساسی پروژه ChangeFlow

## اصول بنیادین

### I. توسعه مبتنی بر Specification

تمام قابلیت‌ها و تغییرات رفتاری MUST براساس Specification تأییدشده توسعه یابند.
Specification هر قابلیت MUST رفتار مورد انتظار، محدودیت‌ها، نیازمندی‌های عملکردی،
سناریوهای پذیرش، معیارهای موفقیت و مسیرهای خطای مرتبط را مشخص کند.

هر تغییر در رفتار محصول MUST پیش از پیاده‌سازی در Specification ثبت شود. Coding Agent
نباید نیازمندی محصولی، رفتار مبهم یا تصمیم معماری را بدون ثبت و تأیید انتخاب کند.

پیش از پذیرش پیاده‌سازی، انطباق آن با این Constitution، Specification، Plan، Tasks و
Acceptance Scenarioها MUST بررسی شود.

**دلیل:** در SDD، کد نتیجه تصمیم‌های مستند و قابل ردیابی است و نباید منبع تعریف رفتار
محصول باشد.

### II. معماری یکپارچه لایه‌ای و سازمان‌دهی Feature-based

سامانه MUST به‌صورت یک Layered Monolith پیاده‌سازی شود. استفاده از Modular Monolith،
Microservices یا سرویس‌های مستقل در محدوده فعلی مجاز نیست، مگر اینکه یک نیازمندی
تأییدشده ایجاد و Constitution و Plan متناسب با آن اصلاح شوند.

مرزبندی سطح‌بالای Solution MUST براساس پروژه‌ها و لایه‌های تعریف‌شده در این سند باشد.
درون هر پروژه، کدها MUST براساس Feature سازمان‌دهی شوند. فایل‌های یک قابلیت باید در
پوشه همان قابلیت قرار گیرند و نباید صرفاً براساس نوع فنی در پوشه‌های عمومی و نامرتبط
پراکنده شوند.

سازمان‌دهی Feature-based نباید مرز لایه‌ها یا قواعد وابستگی میان پروژه‌ها را نقض کند.

**دلیل:** Layered Monolith محدوده فعلی را ساده نگه می‌دارد و سازمان‌دهی Feature-based
از پراکندگی اجزای مرتبط جلوگیری می‌کند.

### III. پلتفرم فنی ثابت

زبان اصلی پیاده‌سازی MUST زبان C#، چارچوب HTTP API MUST چارچوب ASP.NET Core و Target
Framework تمام پروژه‌های قابل اجرا و کتابخانه‌ای MUST برابر `net11.0` باشد.

تمام پروژه‌های Solution MUST از نسخه سازگار و یکسانی از .NET استفاده کنند. نسخه SDK
مورد استفاده برای Build و Test MUST در مخزن تثبیت شود تا محیط توسعه و CI خروجی قابل
بازتولید داشته باشند.

تغییر زبان اصلی، چارچوب API یا نسخه اصلی .NET یک تغییر معماری محسوب می‌شود و MUST پیش
از پیاده‌سازی از طریق اصلاح Constitution و تحلیل اثر آن تأیید شود.

**دلیل:** تثبیت پلتفرم از تصمیم‌های فنی ناسازگار جلوگیری و Build و Test را قابل
بازتولید می‌کند.

### IV. مرزبندی مسئولیت‌ها و جهت وابستگی‌ها

`ChangeFlow.Core.Domain` MUST شامل موجودیت‌ها، اشیای مقداری، ناورداهای ذاتی دامنه و
قواعد معتبر انتقال وضعیت باشد. این پروژه MUST از تمام پروژه‌های دیگر Solution مستقل
باشد.

`ChangeFlow.Core.Application` MUST شامل موارد کاربرد، هماهنگی عملیات، کنترل مجوزهای
وابسته به کاربر جاری و قراردادهای موردنیاز برای سرویس‌ها و زیرساخت‌های بیرونی باشد.
این پروژه MAY فقط به `ChangeFlow.Core.Domain` وابسته باشد.

`ChangeFlow.Infra.DataAccess` MUST جزئیات Persistence، Repositoryها و دسترسی عملیاتی به
داده را پیاده‌سازی کند و MAY به Application و در صورت نیاز Domain وابسته باشد.

`ChangeFlow.Endpoints.Api` MUST مسئول دریافت و اعتبارسنجی اولیه ورودی HTTP، تبدیل
قراردادهای API، فراخوانی Application، تولید پاسخ HTTP، Dependency Injection و
Composition باشد. این پروژه MAY برای Composition به Application و Infrastructure
وابسته باشد.

وابستگی چرخه‌ای ممنوع است. وابستگی مستقیم میان پروژه‌های Infrastructure بدون تصمیم
معماری مستند ممنوع است. Endpoint و Infrastructure MUST فاقد تصمیم‌گیری مستقل
کسب‌وکار باشند و نباید منطق Domain یا Application را تکرار کنند.

ناورداهای مستقل از هویت کاربر یا سرویس بیرونی MUST در Domain اعمال شوند. قواعد وابسته
به کاربر جاری، نقش‌ها، مالکیت منبع یا هماهنگی چند مؤلفه MUST در Application اعمال شوند.

**دلیل:** جهت وابستگی یک‌طرفه و مسئولیت روشن، منطق کسب‌وکار را از جزئیات اجرایی مستقل
و قابل آزمون نگه می‌دارد.

### V. احراز هویت، مجوز و تفکیک وظایف

تمام عملیات محافظت‌شده MUST هویت کاربر، نقش‌ها و مجوزهای فعلی، مالکیت منبع و وضعیت
فعلی درخواست را در سمت سرور بررسی کنند. محدودیت رابط کاربری جایگزین کنترل مجوز در
Application نیست.

مجوز MUST هنگام اجرای هر عملیات ارزیابی شود و نباید صرفاً به بررسی انجام‌شده در مرحله‌ای
پیشین اتکا کند. عملیات فاقد مجوز MUST بدون تغییر وضعیت یا داده رد شود.

فرایند بررسی درخواست تغییر MUST اصل تفکیک وظایف را رعایت کند. هیچ کاربری نباید درخواست
متعلق به خود را تأیید کند؛ این ممنوعیت حتی در صورت داشتن هم‌زمان نقش‌های `Requester` و
`Reviewer` برقرار است.

Permission Matrix و رفتار دقیق هر عملیات MUST در Specification ثبت و با آزمون خودکار
اعتبارسنجی شود.

**دلیل:** صحت گردش تأیید به استقلال Reviewer و اجرای مجوزها در سمت سرور وابسته است.

### VI. انتقال صریح وضعیت و حفاظت از ناورداها

وضعیت Change Request MUST فقط از طریق عملیات صریح Domain و مطابق transitionهای
تأییدشده در Specification تغییر کند. تغییر مستقیم وضعیت از Endpoint، Persistence،
Mapping یا عملیات عمومی ویرایش ممنوع است.

هر عملیات تغییر وضعیت MUST وضعیت مبدأ، هویت و مجوز کاربر، محدودیت مالکیت، اصل تفکیک
وظایف، نسخه داده و ناورداهای Domain را پیش از ثبت تغییر بررسی کند. شکست هر بررسی MUST
عملیات را بدون تغییر وضعیت یا ثبت داده ناقص متوقف کند.

Change Request در وضعیت `Approved` MUST تغییرناپذیر باشد. بازگشایی، لغو یا اصلاح
درخواست تأییدشده فقط با Specification تأییدشده و transition صریح جدید مجاز است.

جزئیات state machine MUST در Specification تعریف شوند و پیاده‌سازی نباید transition
تعریف‌نشده یا ضمنی ایجاد کند.

**دلیل:** تغییر وضعیت رفتار اصلی دامنه است و نباید از مسیرهای جانبی یا بدون اجرای
قواعد کسب‌وکار انجام شود.

### VII. کنترل هم‌زمانی و یکپارچگی داده

تمام عملیات تغییردهنده داده MUST تعارض ناشی از تغییرات هم‌زمان را شناسایی کنند. هیچ
درخواست مبتنی بر نسخه قدیمی نباید تغییر جدیدتر را به‌صورت بی‌صدا بازنویسی کند.

در صورت تشخیص تعارض، عملیات MUST بدون ایجاد تغییر ناقص یا وضعیت ناسازگار متوقف شود و
نتیجه‌ای صریح و قابل تشخیص به فراخواننده بازگرداند.

عملیات تغییر وضعیت MUST اتمیک باشند؛ بررسی وضعیت، بررسی مجوز، بررسی نسخه و ذخیره وضعیت
جدید باید یکپارچگی داده را در برابر درخواست‌های هم‌زمان حفظ کنند.

روش فنی کنترل هم‌زمانی MUST در `research.md` و `plan.md` انتخاب و دلیل آن مستند شود.
رفتار قابل مشاهده تعارض MUST در Specification تعریف و با آزمون خودکار اعتبارسنجی شود.

**دلیل:** جلوگیری از lost update و وضعیت ناسازگار یکی از الزامات قطعی سامانه است.

### VIII. امنیت، مشاهده‌پذیری و حفاظت از اطلاعات

رمز عبور، token، API key، secret و اطلاعات احراز هویت MUST NOT در کد منبع یا Log ثبت
شوند. تنظیمات محرمانه MUST از منبع پیکربندی امن و خارج از کد دریافت شوند.

خطاهای غیرمنتظره و شکست‌های عملیاتی MUST با اطلاعات زمینه‌ای کافی و شناسه هم‌بستگی
ثبت شوند. Logها MUST امکان ردیابی یک درخواست را فراهم کنند، بدون آنکه اطلاعات حساس را
افشا کنند.

خطاهای مورد انتظار کسب‌وکار نباید به‌عنوان خطای سیستمی ثبت شوند. جزئیات داخلی Exception
نباید بدون کنترل در پاسخ HTTP افشا شود.

**دلیل:** مشاهده‌پذیری برای عیب‌یابی ضروری است، اما نباید موجب افشای اطلاعات یا تولید
Logهای گمراه‌کننده شود.

### IX. آزمون‌پذیری و اعتبارسنجی

هر Functional Requirement و Acceptance Scenario تأییدشده MUST آزمون خودکار متناظر
داشته باشد. قواعد Domain و موارد کاربرد Application MUST شامل آزمون مسیر موفق، مسیر
ردشده و شرایط مرزی مرتبط باشند.

سناریوهای ایجاد Draft، Submit معتبر، رد Self-Approval، تأیید توسط Reviewer مستقل، رد
ویرایش Approved و تشخیص Concurrency Conflict MUST با آزمون خودکار پوشش داده شوند.

در آزمون‌های حساس، علاوه بر پاسخ HTTP، وضعیت ذخیره‌شده داده نیز MUST بررسی شود. هر باگ
تأییدشده MUST با Regression Test پوشش داده شود.

آزمون‌های Domain و Application MUST بدون اجرای HTTP Server و بدون اتصال واقعی به
سرویس‌های بیرونی قابل اجرا باشند. شکست Build، آزمون یا کنترل‌های الزامی MUST مانع
پذیرش تغییر شود.

**دلیل:** رفتار قابل اثبات و خروجی آزمون واقعی، معیار اعتبارسنجی پیاده‌سازی در SDD است.

### X. سادگی و توسعه تدریجی

طراحی MUST ساده‌ترین ساختاری باشد که نیازمندی‌های تأییدشده فعلی را برآورده می‌کند.
ایجاد پروژه، لایه، abstraction، dependency یا infrastructure جدید بدون use case فعلی و
دلیل مستند ممنوع است.

قابلیت‌های AI، RAG، MCP و Multi-Agent خارج از Scope فعلی هستند و نباید به‌صورت
پیش‌دستانه وارد معماری یا پیاده‌سازی شوند.

محصول دیتابیس، ORM، روش Persistence، مکانیزم Authentication و روش فنی Concurrency
MUST براساس نیازهای Specification در `research.md` بررسی و در `plan.md` انتخاب شوند.
این Constitution محصول دیتابیس مشخصی را الزام نمی‌کند.

**دلیل:** پیچیدگی زودهنگام هزینه نگهداری را افزایش می‌دهد و برخلاف هدف توسعه تدریجی
پروژه است.

## ساختار الزامی Solution

ساختار سطح‌بالای پروژه MUST به شکل زیر باقی بماند:

```text
ChangeFlow/
├── ChangeFlow.slnx
├── src/
│   ├── 01.Core/
│   │   ├── Domain/
│   │   │   └── ChangeFlow.Core.Domain.csproj
│   │   └── Application/
│   │       └── ChangeFlow.Core.Application.csproj
│   ├── 02.Infra/
│   │   └── DataAccess/
│   │       └── ChangeFlow.Infra.DataAccess.csproj
│   └── 03.Endpoints/
│       └── Api/
│           └── ChangeFlow.Endpoints.Api.csproj
├── tests/
│   └── ChangeFlow.Tests/
└── .specify/
```

نام پروژه‌ها و ساختار سطح‌بالای Solution MUST بدون تغییر باقی بماند. افزودن، حذف یا
تغییر نام پروژه فقط در پاسخ به نیازمندی تأییدشده، همراه با تصمیم معماری مستند و اصلاح
این Constitution مجاز است.

## فرایند SDD و کنترل کیفیت

چرخه توسعه هر قابلیت MUST شامل مراحل زیر باشد:

1. `Specify`: تعریف User Storyها، نیازمندی‌ها، سناریوهای پذیرش و معیارهای موفقیت.
2. `Clarify`: حل ابهام‌های اثرگذار و ثبت تصمیم‌ها و فرض‌ها.
3. `Plan / Research`: طراحی معماری، مدل داده، قرارداد API، Persistence، Authorization
   و Concurrency همراه با دلیل تصمیم‌ها.
4. `Tasks`: تبدیل Plan به کارهای اجرایی، قابل ردیابی و دارای وابستگی مشخص.
5. `Analyze`: بررسی read-only سازگاری Constitution، Specification، Plan و Tasks.
6. `Implement`: پیاده‌سازی مرحله‌ای و فقط براساس Taskهای تأییدشده.
7. `Build / Test / Validation`: اجرای Build و آزمون‌ها و ثبت نتایج واقعی.
8. `Converge`: مقایسه کد با Intent مستند و تبدیل شکاف‌ها به Task قابل ردیابی.

مرحله Analyze نباید مستقیماً Artifactها یا کد را اصلاح کند. مرحله Converge نباید
مستقیماً کد را تغییر دهد و MUST کار باقی‌مانده را به Task مشخص تبدیل کند.

پیش از Plan و Implement، هر ابهام اثرگذار MUST از طریق Clarify حل شود یا به‌عنوان
Assumption صریح، قابل بازبینی و دارای اثر مشخص در Specification ثبت شود.

رفتار تعریف‌نشده، از جمله حذف Draft، مشاهده درخواست‌های دیگران، لغو مجوز یا رفتار
درخواست تکراری، نباید بدون تصمیم مستند پیاده‌سازی شود.

هر Assumption MUST شرح، دلیل، دامنه اثر، ریسک و شرایط بازبینی داشته باشد و نباید با
قواعد قطعی محصول یا این Constitution تعارض داشته باشد.

## Governance

این Constitution مرجع اصول پایدار و الزام‌آور پروژه است و بر Specification، Plan و
Tasks اولویت دارد. هر تعارض MUST پیش از Implement رفع و نتیجه آن مستند شود.

تصمیم‌های فنی مصوب نسخه اولیه در [خط مبنای فنی](technical-baseline.md) ثبت می‌شوند.
Plan هر قابلیت MUST با آن سازگار باشد. تغییر خط مبنا MUST همراه با دلیل، بررسی گزینه‌ها
در Research و تحلیل اثر بر Plan، کد و آزمون‌ها ثبت شود. در صورت تعارض، این Constitution
اولویت دارد؛ تغییر خط مبنا به‌تنهایی نباید اصول این Constitution را تغییر دهد.

اصلاح Constitution MUST شامل دلیل تغییر و تحلیل اثر آن بر Specificationها، Planها،
Tasks، Code و Tests باشد. تغییرات MUST براساس Semantic Versioning نسخه‌گذاری شوند:

- `MAJOR`: حذف یک اصل یا بازتعریف ناسازگار آن؛
- `MINOR`: افزودن اصل یا بخش جدید یا گسترش معنادار الزام‌ها؛
- `PATCH`: شفاف‌سازی، اصلاح نگارشی یا تغییر غیرمعنایی.

عدم رعایت یک اصل فقط با استثنای مستند مجاز است. هر استثنا MUST شامل اصل نقض‌شده، دلیل،
محدوده، ریسک، تأییدکننده و تاریخ انقضا باشد. استثنای دائمی نیازمند اصلاح Constitution
است.

انطباق با Constitution MUST در مراحل Analyze، پیش از Implement و پیش از پذیرش نهایی
بررسی شود. مستندات MUST تصمیم‌ها، دلایل و آثار آن‌ها را به‌صورت روشن و قابل ردیابی ثبت
کنند.
