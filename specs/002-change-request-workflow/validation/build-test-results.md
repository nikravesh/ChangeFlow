# گزارش اجرای اعتبارسنجی فیچر ۰۰۲

تاریخ اجرا ۲۰۲۶-۱۱-۱۶. اجرای محلی روی Windows با SDK موقت `11.0.100`، هدف `net11.0` و SQLite فایل‌محور انجام شد. فرمان‌های جدول از ریشهٔ مخزن با همین SDK اجرا شدند.

| فرمان | نتیجهٔ اجرای نهایی |
|---|---|
| `dotnet restore ChangeFlow.slnx` | موفق |
| `dotnet build ChangeFlow.slnx --no-restore` | موفق، صفر خطا و صفر هشدار |
| `dotnet test ChangeFlow.slnx --no-build --filter 'FullyQualifiedName~ChangeFlow.Tests.ChangeRequests'` | موفق، ۴۸ آزمون قبول، صفر شکست و صفر ردشده |
| `dotnet test ChangeFlow.slnx --no-build` | موفق، ۸۹ آزمون قبول، صفر شکست و صفر ردشده |

## اجرای مسیرهای Quickstart

| مسیر | شواهد اجرای خودکار |
|---|---|
| ۱ — ایجاد، ویرایش و Submit | قرارداد HTTP و بررسی مالک، محتوای trim‌شده و نسخه |
| ۲ — Review و ارسال مجدد | RequestChanges، بازخورد مالک، Edit، Submit مجدد، Approve و دو تصمیم مرتب |
| ۳ — خطا، احراز هویت و مرز عملیات | اعتبارسنجی Bearer و شکل ورودی، منع Self-Review، تقدم تعارض نسخه، کنترل دادهٔ پایدار، هفت مسیر مصوب و قرارداد Setup |
| ۴ — دسترسی به تاریخچه | مالک، Reviewer دارای تصمیم، Reviewer دیگر، حساب بدون نقش لازم و لغو نقش با توکن قبلی |
| ۵ — رقابت و اتمیک بودن | رقابت Edit/Submit و دو Reviewer روی یک نسخه، شکست درج تصمیم، rollback و ترتیب commit لغو نقش |
| ۶ — مهاجرت و راه‌اندازی مجدد | فایل خالی و ارتقا از دیتابیس دارای کاربران و نقش‌های ۰۰۱، اجرای دوبارهٔ Migration و حفظ درخواست و تصمیم‌ها |
| ۷ — معیارهای موفقیت | SC-003، SC-004، SC-006 و SC-007 با آزمون‌های خودکار بررسی شدند. SC-001، SC-002 و SC-005 در انتظار سنجش کاربری هستند. |

برای ساخت فایل قدیمی در آزمون ارتقا، از عملیات Migration اصلی ۰۰۱ و شناسهٔ ذخیره‌شدهٔ همان نسخه استفاده شد. EF شناسهٔ قدیمی ۱۲ رقمی را در جست‌وجوی Migration هدف‌دار پیدا نمی‌کند. ارتقا و اجرای دوباره از طریق `MigrateAsync()` انجام شدند.

## موارد اجرا‌نشده

- اجرای دستی `dotnet run` با صادرکنندهٔ هویت مستقل در محیط آزمایشی تنظیم‌شده انجام نشد. اجرای فنی مسیرهای ۱ تا ۶ با میزبان آزمایشی HTTP و توکن‌های امضاشدهٔ آزمایشی ثبت شد.
- برای SC-001، SC-002 و SC-005 دادهٔ کاربران نماینده و جلسهٔ سنجش در دسترس نبود. در این اجرا زمان یا نرخ موفقیت انسانی گزارش نشده است. معیارهای پذیرش و نگاشت آزمون‌ها در [ردیابی اعتبارسنجی](requirements-traceability.md) آمده‌اند.


## اعتبارسنجی فاز ۷

- T028 — آزمون مسیر واقعی POST /change-requests با تنظیم Authority و Audience از پیکربندی قبول شد. JwtBearer سند OpenID و JWKS را از میزبان مستقل آزمایشی دریافت کرد و توکن RSA را پذیرفت. میزبان درون فرایند و از طریق backchannel آزمایشی اجرا شد و کلید مستقیماً به JWT options تزریق نشد. TLS شبکه و صادرکنندهٔ محیط استقرار در این اجرا پوشش داده نشدند.
- T029 — دو POST با محتوای یکسان و مالک یکسان، دو پاسخ 201، دو شناسه مستقل و برای هر رکورد نسخهٔ ۱ تولید کردند. هر دو رکورد در SQLite مشاهده شدند.
- آزمون ۴۰ حساب — ۲۰ Requester و ۲۰ Reviewer، ۲۰ درخواست Approved و ۴۰ تصمیم ثبت کردند. حذف فایل SQLite اختصاصی پس از پایان موفق آزمون تأیید شد. این اجرا سنجش کاربری SC-001، SC-002 و SC-005 را تکمیل نمی‌کند.

در اجرای نهایی با SDK 11.0.100، dotnet build ChangeFlow.slnx --no-restore با صفر خطا و هشدار، سه آزمون فاز ۷ با فیلتر نام آزمون، و dotnet test ChangeFlow.slnx --no-build با ۹۲ آزمون موفق پایان یافتند.

## آزمون تکمیلی TLS محلی

آزمون خواندن OpenID metadata و JWKS با صادرکنندهٔ مستقل Kestrel روی HTTPS واقعی loopback اجرا شد. backchannel به گواهی موقت همان آزمون اعتماد محدود داشت. سپس API در TestServer توکن RSA را پذیرفت و POST /change-requests پاسخ 201 داد. آزمون متمرکز در هر دو حالت درون‌فرایندی و TLS شبکه موفق شد. اجرای کامل dotnet test ChangeFlow.slnx --no-build با ۱۰۲ آزمون موفق پایان یافت. این اجرا اعتبار TLS و صادرکنندهٔ محیط استقرار یا معیارهای انسانی را تأیید نمی‌کند.
