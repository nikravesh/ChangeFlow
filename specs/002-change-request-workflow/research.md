# پژوهش طراحی فیچر ۰۰۲

منابع داخلی شامل [Constitution](../../.specify/memory/constitution.md)، [Technical Baseline](../../docs/architecture/technical-baseline.md) و [پژوهش فیچر ۰۰۱](../001-user-role-management/research.md) هستند. تصمیم‌های مصوب در Plan ارجاع داده شده‌اند.

## R1 — هویت و نقش جاری

**تصمیم** — گروه مسیرهای ۰۰۲ از ASP.NET Core JWT Bearer با یک صادرکنندهٔ مورد اعتمادِ پیکربندی‌شده استفاده می‌کند. اعتبار امضا، صادرکننده، مخاطب و انقضا بررسی می‌شود. قرارداد اتصال ملزم می‌کند که صادرکننده مقدار تغییرناپذیر `sub` را از شناسهٔ داخلی `UserId` حسابِ تأییدشده تنظیم کند. اتصال حساب هنگام آماده‌سازی هویت از کانال مدیریتی مورد اعتماد انجام می‌شود. هویت بیرونی بدون حساب محلی پذیرفته نمی‌شود. Application نقش‌ها را از حساب محلی دوباره می‌خواند و نقش‌های توکن را در نظر نمی‌گیرد. راه‌اندازی عملیاتی به صادرکننده و برقراری این اتصال نیاز دارد.

**دلیل انتخاب** — قابلیت ۰۰۱ ثبت کاربر و نقش را فراهم می‌کند. مسیر `POST /users` قرارداد Setup Code خودش را حفظ می‌کند. اتصال به صادرکننده، بررسی هویت را از مجوز مبتنی بر نقش جاری و از مدیریت رمز عبور جدا می‌کند. سیاست Bearer فقط به مسیرهای ۰۰۲ اعمال می‌شود.

**گزینه‌های جایگزین بررسی‌شده** — صدور توکن و ورود محلی، چرخهٔ مدیریت نشست و رمز را به Scope فعلی اضافه می‌کند. Setup Code هویت فردی ندارد. اتصال با نام ورود یا ایمیل به شناسهٔ قابل‌تغییر متکی است. جدول نگاشت `iss/sub` برای صادرکننده‌ای که نمی‌تواند شناسهٔ محلی را به‌شکل امن در subject تثبیت کند، گزینهٔ بازبینی است.

راهنمای رسمی [پیکربندی JWT Bearer در ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication).

**کاندید Technical Baseline پروژه** — جداسازی Authentication از Authorization قبلاً مصوب است. تصمیم تازهٔ قابل بازبینی، قرارداد هویت Bearer با صادرکنندهٔ معتبر و اتصال subject به UserId محلی برای APIهای محافظت‌شده است. پذیرش سراسری نیازمند اثبات امکان اتصال حساب، گردش کلید و تنظیم issuer/audience در محیط است. مسیر Setup فیچر ۰۰۱ همچنان قرارداد خودش را دارد.

## R2 — ذخیره‌سازی و Migration

**تصمیم** — برای اجرای محلی ۰۰۲ همان SQLite فایل‌محور، EF Core، DbContext و مسیر اجرای Migration فیچر ۰۰۱ استفاده می‌شود. Migration افزایشی فقط جداول و قیود مدل ۰۰۲ را اضافه می‌کند و باید روی فایل خالی و فایل دارای داده و Migration فیچر ۰۰۱ آزموده شود.

**دلیل انتخاب** — وضعیت درخواست، تاریخچه و منبع نقش جاری در یک datastore و مرز تراکنش قرار می‌گیرند. اجرای محلی با محیط فعلی مخزن هم‌راستاست.

**گزینه‌های جایگزین بررسی‌شده** — دیتابیس جدا برای فیچر، اتمیک‌بودن تصمیم با نقش جاری را دشوار می‌کند. تغییر به PostgreSQL یا SQL Server نیازمند مهاجرت داده و آزمون سازگاری فیچر ۰۰۱ است. EF InMemory رفتار تراکنش و قید رابطه‌ای را بازنمایی نمی‌کند.

## R3 — نسخه، تراکنش و نتیجهٔ رقابت

**تصمیم** — نسخهٔ درخواست عدد مثبت داخلی با افزایش یک واحد پس از هر تغییر موفق و concurrency token در EF Core است. در HTTP نسخه به شکل رشتهٔ ده‌دهی مبادله می‌شود تا دقت مشتری‌ها حفظ شود. عملیات روی درخواست موجود `expectedVersion` دریافت می‌کند و اختلاف نسخه به `409 version_conflict` نگاشت می‌شود. SQLite برای تغییر، تراکنش کوتاه non-deferred روی همان اتصال و DbContext را پیش از خواندن حساب و نقش جاری و درخواست آغاز می‌کند. Application اعتبار هویت و مجوز، سپس نسخه و وضعیت را بررسی می‌کند و Domain تغییر را اعمال می‌کند. تصمیم Review و تغییر درخواست با هم commit می‌شوند. خواندن تاریخچه از snapshot واحد برای بررسی مجوز و ساخت پاسخ استفاده می‌کند.

**دلیل انتخاب** — شرط نسخه درخواست قدیمی Client را شناسایی می‌کند و تراکنش، تغییر نقش و تغییر درخواست را در SQLite به ترتیب قطعی commit می‌رساند. پس از مشاهدهٔ نسخهٔ قدیمی، Client باید دوباره بخواند. Busy/Locked فقط در صورت rollback قطعی و در بودجهٔ محدود با context و تراکنش جدید و همان نسخهٔ مورد انتظار تکرار می‌شود. بعد از اتمام بودجه، بررسی تازه و مجاز می‌تواند اختلاف واقعی نسخه را به 409 تبدیل کند. اگر اختلاف قابل‌اثبات نباشد، قفل موقت 503 است. نتیجهٔ نامعلوم commit باعث تکرار خودکار عملیات نمی‌شود.

**گزینه‌های جایگزین بررسی‌شده** — توکن خودکار دیتابیس در SQLite دردسترس نیست. نسخهٔ GUID ترتیب Revision را بیان نمی‌کند. فقط concurrency token درخواست، رقابت با تغییر نقش را پوشش نمی‌دهد. تراکنش deferred برای تغییر ممکن است در ارتقای خواندن به نوشتن شکست بخورد. `If-Match` و `412` گزینهٔ معتبر قرارداد HTTP‌اند. فیلد بدنه یک پیش‌شرط یکسان برای Edit و فرمان‌های POST فراهم می‌کند.

راهنماهای فنی [EF Core concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) و [Microsoft.Data.Sqlite transactions](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/transactions).

## R4 — قرارداد HTTP گردش کار

**تصمیم** — از گروه Minimal API موجود در پروژه برای ایجاد، خواندن مستقیم، ویرایش، فرمان‌های صریح و تاریخچه استفاده می‌شود. نمایش درخواست جاری و تاریخچه دو مسیر مجزا دارند. خطاهای عملیات طبق ProblemDetails و جدول قرارداد نگاشت می‌شوند.

**دلیل انتخاب** — جداسازی خواندن تاریخچه، مجوز متفاوت آن را قابل آزمون می‌کند. فرمان‌های صریح امکان تغییر مستقیم وضعیت از payload را حذف می‌کنند. مسیرهای مبتنی بر شناسه از فرض فعلی دربارهٔ دریافت شناسه پیروی می‌کنند.

**گزینه‌های جایگزین بررسی‌شده** — قراردادن تاریخچه در پاسخ عمومی درخواست ریسک افشای آن به Reviewer بدون تصمیم را بالا می‌برد. PATCH وضعیت، مرز میان Edit و فرمان‌های Domain را مبهم می‌کند. Controller در این فیچر قابلیت موردنیاز اضافه‌ای ایجاد نمی‌کند.

تصمیم‌های R2 تا R4 در محدودهٔ این فیچر و محیط محلی‌اند. انتخاب Provider و استراتژی عملیاتی Production در سطح پروژه باز است.
